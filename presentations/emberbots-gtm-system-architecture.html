GTM System Architecture

Do not build one giant sales bot. Build a multi-agent GTM machine.

This presentation translates the Ember Bots GTM architecture into a shareable format for review, planning, and execution. The system is designed for home-services first, with Ember CRM as the system of record and human approval at the right external-action edges.

Market
Owner-led HVAC and plumbing first
Model
Multi-agent GTM operating system
Brain
Ember CRM as the shared truth layer
Control
Human-approved sends and commitments first
Core recommendation

What this system should do

  • run lead generation, qualification, outbound, inbound, and pipeline ops
  • keep context shared across agents
  • prevent low-quality outreach
  • keep Steve focused on real conversations and closing
Top-level architecture

CRM-centered orchestration with specialized agents and controlled external actions

The architecture works because each agent has a narrow job, shared context flows through CRM, and orchestration prevents premature outreach or sloppy handoffs.

Core layers

The system has four critical layers before any “AI sales bot” claim becomes real

1. Signal capture layer

Collect and normalize signals from Maps, website forms, chat, email, phone/Vapi, manual entry, and later SMS/ad channels.

  • normalized lead payloads
  • source + channel metadata
  • timestamps + evidence fields

2. Agent orchestration layer

Routes work, enforces progression, prevents premature outreach, and creates approval queues.

  • task routing
  • state management
  • review queue creation

3. Ember CRM as system of record

Holds lead truth, preserves cross-agent context, and supports visibility and approval decisions.

  • use existing Lead object first
  • do not split into Prospect in phase 1
  • store evidence, stage, notes, next action

4. Human approval layer

Keeps external actions controlled early while agents handle research, drafting, scoring, and prioritization.

  • humans approve sends, calls, proposals
  • autonomy expands later by approved lead class
Specialized agents

Five agents, one shared brain

This system only works if each agent owns a narrow, reliable job instead of trying to be one fuzzy all-purpose “sales AI.”

Lead Sourcing Agent

Finds and enriches high-quality local operators that match the ICP.

  • Maps-first sourcing
  • territory and trade filtering
  • owner-led validation
  • weak-follow-up signal detection

Qualification Agent

Decides whether a lead is real, relevant, and safe for outreach.

  • fit scoring
  • evidence verification
  • stage assignment
  • reject / park / advance

Outbound Agent

Prepares personalized first-touch and follow-up logic for human-approved sends.

  • email drafts
  • call prep briefs
  • cadence logic
  • CTA recommendations

Inbound Response Agent

Handles website, chat, email, and phone interest fast and consistently.

  • instant qualification
  • routing to meeting / nurture / escalate
  • CRM record creation or update

Sales Operator Agent

Acts as the internal sales manager layer on top of the pipeline.

  • daily priority queue
  • stalled-deal alerts
  • meeting prep
  • proposal draft packages

Shared design rule

Every agent writes to the same truth layer instead of maintaining separate hidden state.

  • lead state
  • channel history
  • qualification rationale
  • last action + next action
CRM field model

The CRM must hold enough structured state for agents to coordinate reliably

Identity + fit

  • company name
  • contact name
  • trade
  • territory
  • owner-led / local proof

Evidence + workflow

  • source + source detail
  • weak-follow-up evidence
  • qualification score
  • stage
  • last touch / next action

Revenue ops state

  • meeting booked
  • proposal status
  • suggested package
  • objection notes
  • assigned owner
Workflow architecture

Outbound and inbound flows should meet in the same operating system

Outbound workflow

  • sourcing agent creates candidate lead
  • qualification agent validates and scores it
  • CRM stores evidence and stage
  • outbound agent drafts first touch + follow-up
  • human approves send
  • outcome logs back into CRM
  • sales operator reprioritizes next steps

Inbound workflow

  • website/chat/phone/email event arrives
  • inbound response agent qualifies it
  • CRM creates or updates record
  • route to book / nurture / qualify more / escalate
  • sales operator surfaces highest-value opportunities
Offer architecture

Sell the business outcome, not generic AI automation

Entry offer

Missed Revenue Snapshot is the diagnostic wedge. It creates an evidence-grounded first conversation and lowers the friction of initial outreach.

Core paid offer

Lead Recovery & Response System improves response speed, reduces lead leakage, and cleans up estimate follow-up and customer communication flow.

Phase plan

Build usability first, autonomy second

Phase 1
Sourcing, qualification, inbound intake, outbound drafts, sales operator dashboard
Phase 2
Semi-autonomous follow-up, inbox triage, booking workflow, approved-class outbound
Phase 3
Cross-channel nurture, reactivation, proposal generation, deeper orchestration
Phase 4
Full revenue ops: onboarding, review generation, reactivation, account expansion
Hard truth

If Ember tries to build one giant “sales bot,” it will be vague, brittle, and hard to trust.

If Ember builds a coordinated GTM system with specialized agents, CRM as the shared brain, human approval at the right edges, and a narrow home-services wedge first, it has a realistic path to becoming a usable sales and marketing operating machine.
